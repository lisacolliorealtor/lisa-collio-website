## Build Record Standard (locked, July 2026)

Every generated artifact — every processed image, every regenerated featured image, every derived file — must have a recorded build job stating its source, parameters, and how to reproduce it exactly. An artifact with no build record becomes unreproducible the moment it needs to change, and recovering one after the fact means reverse-engineering it by hash-matching against every candidate source — expensive, and never fully certain.

This applies to any current or future generated-asset pipeline (`SECTION_JOBS`, `OVERLAY_JOBS`, or their successors): when a script produces a file, the job that produced it is committed in the same change. No asset ships without its build record.

## Verification Standard (locked, July 2026)

A report states what was actually measured, not what the measurement is assumed to prove. This project has repeatedly generated true-but-misleading reports: a count that was accurate for the field class actually measured, presented as if it covered a broader claim. Before reporting a number as evidence of completeness or correctness:

- State which field, class, or scope was actually checked
- If a check could produce a false positive or false negative, verify against a known case in both directions before trusting it
- A check that never flags anything and a check that flags everything are both worthless; prove the check catches real problems by testing it against a deliberately broken case
- When a "gap" or "mismatch" is found, confirm whether it's a real defect or an artifact of the check itself (e.g., comparing rendered output instead of raw markup, or full-image comparison instead of the region that matters) before reporting it as a finding
- Before running a process across a full batch, prototype it on a small sample that includes at least one already-known answer, report the real hit rate honestly, then decide whether to scale — rather than promising full coverage and discovering the gaps afterward

## EN/ES Parity Standard (locked, July 2026)

English and Spanish content ship in the same PR, verified by a measured count in each language — never assumed equal, never shipped as a follow-up. This project's most serious recurring failure has been Spanish content silently lagging English by a full batch, surfacing only when someone happened to look at the live page. `audit.js` enforces this mechanically for images (EN/ES image-count parity); the same standard applies to any future content class.

Count parity is necessary but not sufficient. A Spanish page can match its English twin's item count while carrying thinner content per item — found in this project as alt text with equal image counts but noticeably less descriptive Spanish strings. When verifying parity, compare substance between paired items, not only counts.

## Field-Class Compliance Coverage Standard (locked, July 2026)

A compliance rule is not enforced project-wide until it has been checked against every field class that can render user-facing text — not just the one class where the problem was first found. This project's Fair Housing sweep found the same category of violation three times in sequence, each discovered independently because a rule built for one field was never checked against its siblings: alt text (missed for months), then body copy (the homepage "quiet residential areas," found only after alt text was fixed), then meta descriptions (missed until a "Realtor Lisa Collio" instance surfaced by chance).

When any content or compliance rule is introduced, explicitly enumerate every field class it should apply to before declaring the rule "done": H1, body copy, alt text, meta description, og/twitter tags, schema fields, captions, button/CTA text, and form labels. A rule proven correct on one class is a prototype, not a standard, until the enumeration is checked.

## Single Open-Items Record Standard (locked, July 2026)

Exactly one open-items/punch-list record exists for this project, lives in the repo, and every session updates it in place. No parallel or competing tracking document is created, even temporarily. This project twice came close to forking its punch list into two live copies within the same week.

Any edit to the open-items record is diffed against its last-known-good version before committing — a bad string-replace can silently delete a section without raising an error, which already happened once to this file.

## Rejected-Asset Standard (locked, July 2026)

When an asset (an image, a piece of copy, a source) is ruled out — confirmed not usable, not compliant, or not authentic — that ruling is recorded as durably as a Build Record, and mechanically enforced so it cannot be silently reversed. An empty slot reads as an oversight to a future session; without a durable, enforced record of *why* it's empty, "helpfully" filling it is close to a certainty, not a remote risk. This project records rejected images in `content/source/rejected-assets.txt`, marks them inline in the relevant manifest, and fails the build if any page references one — that pattern applies to any future class of rejected asset.

## Title/Identity-Text Consistency Sweep Standard (locked, July 2026)

Any change to a page's canonical title or H1 must be verified by a full-text search for the old string returning zero hits sitewide, not by enumerating the fields believed to reference it (title tag, H1, breadcrumb, schema headline, card links, sitemap, `llms.txt`). This project's title/H1 changes needed updating in five to nine separate representations each time, scattered across different files, and "the fields I remembered to update" undercounted at least once. The old string's absence, confirmed by search, is the actual completion criterion — a remembered checklist is not.

## PR Description Currency Standard (locked, July 2026)

A pull request's title and description are re-verified against its actual current diff immediately before merge — never trusted from when they were first written. Approval attaches to what is actually in the diff at merge time, not to an earlier summary of intent, since mid-PR corrections can leave a description describing a decision that was later reversed.
